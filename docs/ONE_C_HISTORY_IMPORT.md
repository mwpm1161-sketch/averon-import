# Импорт истории закупок 1С

## Назначение и границы

Импорт загружает отчёт закупок из XLSX в отдельный нормализованный локальный snapshot. Активный snapshot используется 1C sourcing provider в режимах, описанных в [документации по маршрутизации](ONE_C_HISTORY_ROUTING.md). История остаётся историческим фактом закупки, а не подтверждением текущей цены, наличия или возможности поставки; она не меняет OCR, matcher в целом, Human Review или экспорт спецификации.

Capability `one_c_history_import` доступна ADMIN и USER для операций истории. Новый `/api/one-c-history/**` surface защищён этой capability; совместимые `/api/admin/one-c-history/**` aliases остаются ADMIN-only и используют тот же service layer. `/api/settings`, секреты и provider maintenance остаются ADMIN-only. USER может просматривать/выбирать существующий профиль и менять mapping только для текущего preview/import; только ADMIN может сохранять, обновлять или удалять глобальные профили.

Каждый pending preview связан с создавшим его actor. Inspect, analyze и final import проверяют owner; ADMIN не получает override для чужого preview. Хранятся не более 3 preview на пользователя и 20 всего; истёкшие preview удаляются по TTL, а создание preview одним пользователем не вытесняет чужие. При busy 409 на финальной замене preview и mapping остаются для retry.

## Форматы отчёта и сопоставление

Поддерживаются две структуры:

- `hierarchical_grouped`: отдельная строка группы задаёт номенклатуру и единицу, а следующие строки содержат события до следующей группы. Заголовки группы и события имеют отдельные номера строк и отдельные карты полей: одна физическая колонка может означать название в строке группы и цену в строке события. Автоопределение проверяет соседние строки заголовков в пределах первых 50 строк; объединённые ячейки учитываются, но не являются единственным сигналом для классификации;
- `flat`: одна строка представляет одно событие закупки с повторяющимися полями номенклатуры.

Автоопределение ищет заголовки по семантическим именам, а не по буквам столбцов. Пользователь может выбрать лист, строки заголовков группы и событий, тип структуры и отдельные столбцы каждой роли. В двухуровневом отчёте номенклатура читается только из строки группы; событие без действительной предыдущей группы отклоняется, и парсер не создаёт для него вымышленную позицию. Сохранённый профиль хранит ID, монотонную ревизию, лист, обе строки заголовков, обе карты полей, тип структуры, стратегию разбора названия и подписи каждой строки заголовка. Изменение или удаление профиля не меняет provenance уже активного снимка. Совместимый профиль применяется автоматически, но координаты заголовков всегда берутся из текущего файла. Если несколько совместимых профилей содержат разные сопоставления, пользователь должен выбрать профиль явно; глобально сохранять или менять его может только ADMIN. Если лист или подписи структуры заголовков изменились, автоматическое сопоставление не считается утверждённым: нужно проверить и пересчитать предпросмотр.

Рекомендуется передавать `Номер/код номенклатуры` (`1c_item_code` / `nomenclature_number` или эквивалентное поле из конфигурации 1С). Поле необязательное, чтобы текущий отчёт без кода оставался импортируемым. При отсутствии кода предпросмотр показывает предупреждение: «В отчёте не выгружен код номенклатуры. История будет импортирована, но идентификация одинаковых позиций будет менее надёжной.»

## Идентичность и факты источника

Непустой стабильный код 1С — канонический ключ позиции. События с одинаковым кодом относятся к одной записи номенклатуры, а разные коды остаются разными даже при одинаковых названиях. В иерархической структуре код, артикул, производитель и характеристика из строки группы наследуются событиями, если в строке события поле пустое; исходные групповые и событийные значения сохраняются отдельно. Если групповой и событийный коды противоречат друг другу, каноническим остаётся групповой код, а конфликт отмечается для проверки. Различия единицы или описательных полей у одного кода не исправляются автоматически и отмечаются предупреждением целостности.

Если код не выгружен, идентичность явно помечается `missing_stable_code`. В иерархическом отчёте разные группы сохраняются отдельно, даже когда название и единица совпадают; в плоском отчёте без кода события не склеиваются по названию. Повторная подпись «название + единица» сама по себе не доказывает каноническую идентичность. Текущая SAFE policy может использовать только строгую deterministic source-name+unit политику со source-owned specificity и проверкой неоднозначности; иначе кандидат остаётся REVIEW и при `one_c_then_provider` обрабатывается fallback по правилам маршрутизации. Когда отчёт содержит `1c_item_code`, он служит канонической идентичностью внутри снимка, но не подменяет baseline исходной спецификации.

Сохраняются все события, включая «Авансовый отчет» без поставщика/договора и корректировки без цены. Цены отчёта имеют базис `gross_including_vat` («с НДС»). Числа парсятся в `Decimal`; сообщённая цена и сумма сохраняются отдельно от эффективной цены. При положительном количестве и известной сумме эффективная цена равна `сумма / количество`, чтобы не терять точность исходной суммы при округлении отображённой цены. Событие без сообщённой цены и суммы остаётся в истории с `price_usable=false`, а не превращается в нулевое предложение. Исходные текстовые значения полей остаются в provenance события.

Эффективная цена вычисляется как `amount_gross / quantity` в явном локальном контексте `Decimal` с точностью 50 значащих цифр и округлением `ROUND_HALF_EVEN`. Это детерминированное представление частного, не дополнительное округление до копеек; сериализация не зависит от глобального контекста `Decimal`. Исходные `quantity`, `reported_unit_price_gross` и `amount_gross` сохраняются отдельно. Для отображённой цены проверка использует `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`.

## Результаты локального acceptance gate текущего отчёта

Реальный XLSX был загружен через `OneCHistoryImportService` в отдельный временный `DATA_DIR`, вне git. Обнаружены лист `TDSheet`, 7 599 физических строк, строка заголовка группы 9 и строка заголовка событий 10; импортировано 3 066 групп и 4 523 события. Типы документов: 4 081 «Поступление товаров и услуг», 440 «Авансовый отчет» и 2 «Корректировка поступления». Получены 264 различных непустых контрагента, период 23.06.2026–22.09.2026 и 14 единиц: `шт`, `кг`, `м`, `м2`, `л`, `Пар`, `м3`, `компл`, `пог. м`, `упак`, `г`, `боб`, `т`, `мл`. Все 440 событий авансовых отчётов не содержат контрагента. Обе корректировки сохраняют количество, дату и документ, не содержат сообщённой цены или суммы и имеют `price_usable=false`.

В 1 190 событий произведение отображённой цены на количество отличается от суммы отчёта. Для всех них сохранённая эффективная цена совпала с частным суммы и количества при точности 50 значащих цифр; после округления до копеек методом `ROUND_HALF_UP` она совпадает с отображённой ценой. Число ошибок такой проверки — 0, максимальное абсолютное отличие эффективной цены от отображённой — 0,005 руб./ед.

`repeated_display_label_count` считает различные пары «название + единица», которые повторяются между группами без стабильного кода, после NFKC, `casefold` и схлопывания пробелов; пунктуация сохраняется. По этой семантике в реальном отчёте получилось 27 повторяющихся подписей. `normalized_display_collision_count` отдельно считает совпадающие пары после прежней агрессивной нормализации, удаляющей пунктуацию; получилось 51. Это диагностические метрики, а не правила идентичности: группы и provenance остаются раздельными, число групп номенклатуры остаётся 3 066, предупреждение указывает `missing_stable_code`, а метаданные снимка — `degraded_missing_stable_code`.

Импорт прошёл `PRAGMA integrity_check` (`ok`) без нарушений внешних ключей; mapping provenance и semantic import fingerprint присутствуют. Повторная загрузка того же XLSX с тем же сопоставлением была идемпотентной и не перестроила снимок. Нормализация регистра OOXML `xl/SharedStrings.xml` была задействована во временной копии; временные нормализованные книги и pending XLSX удалены, исходные байты не изменились. В API/public payloads абсолютных локальных путей не обнаружено. Исходный корпоративный XLSX не включён в git.

В принятом TDSheet заголовок группы расположен в строке 9 (`Номенклатура, ед. изм.`), а заголовок событий — в строке 10 (`Цена с НДС`, `Количество`, `Сумма с НДС`, дата, документ прихода, контрагент и договор). В столбце A строки группы содержат наименование, а строки событий — цену; эти значения интерпретируются только по своей роли. В перспективном плоском отчёте можно дополнительно сопоставить артикул, производителя, характеристику, код/ИНН поставщика, ставку НДС, валюту, организацию, стабильную ссылку документа и номер строки без изменения схемы базы.

Семейства единиц определяются общим справочником `core.unit_normalization`: 1С использует консервативные алиасы из отчёта, а sourcing вызывает тот же справочник через совместимый профиль, который сохраняет прежний набор принимаемых алиасов и прежнюю нормализацию. Порог и политика matcher не меняются.

## Предпросмотр, staging и замена снимка

1. XLSX читается потоково с лимитом 25 MiB, рассчитывается SHA-256, проверяются ZIP/OOXML, число частей, общий распакованный объём, степень сжатия, ссылки, листы, размеры и формулы. Макросы, внешние ссылки, формулы и небезопасная структура не исполняются и не принимаются.
2. Сервер показывает ограниченные агрегаты, предупреждения и максимум 12 строк примера. Полный лист не выгружается в DOM. Путь сервера не возвращается клиенту.
3. После изменения карты полей сервер заново разбирает файл и связывает подтверждение импорта с точно проверенной комбинацией листа, строки заголовка, структуры и сопоставления.
4. Подтверждённый импорт строит новую отдельную SQLite-базу во временном staging-файле, проверяет внешние ключи, целостность SQLite и число событий, сбрасывает её на диск и только потом атомарно заменяет активный `history.sqlite3`. Успешный `os.replace` — явная точка фиксации: ошибка до неё сохраняет предыдущий снимок, а сбой последующей синхронизации каталога или записи статуса возвращается как предупреждение об уже активированном новом снимке.
5. Идемпотентный повтор требует совпадения и SHA-256 исходного XLSX, и сохранённого semantic import fingerprint: выбранного листа, структуры, текущих строк заголовков и их подписей, карт полей, стратегии разбора и версии парсера. Переименование профиля или изменение его ревизии без изменения семантики импорта повторной активации не требует; новый лист или исправленное сопоставление того же файла строит и атомарно активирует новый снимок.
6. Временный исходный XLSX хранится в закрытом `.pending` внутри `DATA_DIR/sourcing/one_c/` только пока нужен предпросмотру. Он удаляется после подтверждённого успеха или ошибки; незавершённые предпросмотры имеют ограниченный срок и лимит количества. Узкая нормализация регистра `xl/SharedStrings.xml` выполняется только во временной копии рядом с загрузкой и не меняет исходный файл.

## Хранилище

Импорт и профили отделены от `CatalogRepository` и друг от друга:

- `DATA_DIR/sourcing/one_c/history.sqlite3` — активный заменяемый снимок;
- `DATA_DIR/sourcing/one_c/import_profiles.json` — профили, переживающие замену истории;
- `DATA_DIR/sourcing/one_c/import_status.json` — последняя попытка импорта.

В SQLite разделены таблицы `import_metadata`, `nomenclature_items`, `nomenclature_descriptive_variants` и `purchase_events`. Таблица вариантов сохраняет разные названия/единицы/описательные факты одного стабильного кода для sourcing-поиска. В событии хранятся код/идентичность, исходные название и единица, нормализованное семейство единиц, дата и тип документа, ссылка/номер документа, контрагент, договор, количество, сообщённая и эффективная цена с НДС, сумма, пригодность цены, лист/строка/версия parser и JSON provenance исходных и дополнительных полей. Метаданные включают пропущенные строки и число предупреждений. Это история событий, а не свёрнутый «последний прайс».

## Локальная проверка и ограничения

Синтетические тесты проверяют иерархическую структуру по принятому профилю агрегатов, регистр OOXML shared strings, повторяющиеся подписи групп, стабильные коды, пропущенного поставщика, события без цены, парсинг Decimal и округление, snapshot activation, профиль, безопасность архива и очистку загрузки. Реальный корпоративный файл следует держать вне репозитория и не добавлять в git.

Импорт сам не выполняет запросов к внешним API и не обслуживает sourcing-кеши: направление зависимости остаётся `history snapshot → read provider`. Прочитайте [правила маршрутизации](ONE_C_HISTORY_ROUTING.md) перед интерпретацией исторических совпадений.

## Текущий 1C provider и deterministic safety

`OneCHistoryProvider` зарегистрирован в sourcing runtime и читает активный bounded read model из `history.sqlite3`. Для импорта и чтения используется один application-owned `OneCHistoryRepository`; API не раскрывает source JSON целиком, договоры или файловые пути. Ошибка или повреждение snapshot даёт безопасное unavailable состояние. Правила трёх режимов, fallback и SAFE decision описаны в [ONE_C_HISTORY_ROUTING.md](ONE_C_HISTORY_ROUTING.md).

Чтение и атомарная активация используют один `OneCHistoryRepository` lock. Репозиторий коротко открывает SQLite, читает metadata, номенклатуру, варианты и события ограниченным числом запросов, строит immutable read models и закрывает connection до возврата. `sqlite3.Row`, SQL-поля исходного JSON, договоры и файловые пути не уходят в provider. Ошибка или повреждение активного снимка возвращается как typed unavailable state с безопасным сообщением без пути и деталей SQLite.

Версия каталога — короткий `1c-…` SHA-256 от SHA исходного файла и semantic import fingerprint. Время импорта и имя файла на версию не влияют. Provider лениво строит in-memory projection только при первом чтении версии; повторный поиск по той же версии повторно не загружает события. Новая активированная версия инвалидирует проекцию при следующем поиске. Строитель и поиск синхронно используют immutable snapshot, поэтому не смешивают элементы и события двух активаций.

Поиск проверяет все сохранённые descriptive variants, использует точные артикулы/имена/характеристики и ограниченное RapidFuzz-сходство для retrieval, затем создаёт не более запрошенного лимита (и не более 50) `Offer`: максимум один на canonical `item_id`. Fuzzy similarity расширяет только набор кандидатов и сама по себе не даёт `SAFE_MATCH`. Исходные названия, артикулы и единицы сохраняются в offer/provenance без поисковой нормализации.

Для предложения выбирается самая поздняя пригодная цена: `document_date DESC`, затем `source_row DESC`, затем стабильный `event_id DESC`. Непригодная новая корректировка не заменяет более старую пригодную цену; если пригодных событий нет, кандидат может быть показан без цены и требует REVIEW. Числа остаются `Decimal`. Цена имеет только исторический смысл — ранее зафиксированная закупка на сохранённую дату и в сохранённом базисе, а не текущая цена или предложение.

В provenance передаются только явно выбранные поля исторического события: snapshot version, canonical item ID, качество идентичности, номер группы, выбранное событие и дата закупки, тип документа, контрагент, количество, базис и сообщённая/эффективная цены, а также `currency_basis` (`source` или `company_default`). Не передаются договор или весь `source_facts_json`. Read model сохраняет исходную валюту без изменения, включая пустое значение. Только адаптер `OneCHistoryProvider` для sourcing `Offer` подставляет корпоративную валюту по умолчанию `RUB`, если сопоставленная валюта отсутствует; явно указанная валюта сохраняется и нормализуется `Offer` в верхний регистр. Снимок и импортированные факты не меняются. Доступность всегда `unknown` (`availability=None`), URL пуст, бренд не выводится из производителя. Ни один исторический price не подаётся в текущие project totals.

`lookup()` возвращает отдельное решение `SAFE_MATCH`, `REVIEW` или `NO_MATCH`, не меняя глобальную семантику `OfferMatcher`. SAFE остаётся fail-closed: требуется единственный детерминированный identity, strict matcher result, согласованные item/variant/event facts, известная совместимая единица, пригодная цена и дата, отсутствие обязательных unresolved атрибутов и collision. Основанием служит точный source-backed article либо отдельная exact-name+unit policy с source-owned specificity; fuzzy retrieval само по себе никогда не даёт SAFE. Generic labels, неизвестные единицы, конфликт provenance и неоднозначность остаются REVIEW. В `one_c_then_provider` только SAFE подавляет provider; прочие исходы идут в per-row fallback.

Для проверки единиц используется общий `normalize_unit_family`, включая семейства из реального отчёта (`шт`, `кг`, `м`, `м2`, `л`, `Пар`, `м3`, `компл`, `пог. м`, `упак`, `г`, `боб`, `т`, `мл`). Неизвестные единицы и преобразования между семействами вроде кг↔г и л↔мл не допускаются; прежний `normalize_sourcing_unit_family` для существующих провайдеров не меняется.

Снимки без стабильного кода сохраняют каждую импортированную группу отдельной слабой identity. Совпадение имени и единицы не сливает группы; одинаковые артикулы/имена, которые дают эквивалентное детерминированное evidence в нескольких canonical items, приводят к REVIEW. Для будущих снимков стабильный 1С-код продолжает объединять только принадлежащие ему варианты, но входной `ProductIntent` не трактуется как носитель внутреннего 1С-кода.

Read model также выводит item-level `integrity_conflicts` из source-backed canonical item, descriptive variants и purchase events. Несогласованные известные семейства единиц, артикула, производителя или характеристики, противоречащий canonical stable code у события, отсутствующие descriptive variants и malformed required provenance исключают `SAFE_MATCH`; наружу передаются только общие коды конфликта, никогда конфликтующие корпоративные значения. Для `SAFE_MATCH` семейства `ProductIntent`, выбранного descriptive variant и выбранного price event должны быть известны и совпадать после общей нормализации. Для каждого canonical item дополнительно проверяются все известные семейства единиц из активного снимка. Потерянный набор variants оставляет canonical summary доступным только для `REVIEW`.

Отсутствие отдельного article в отчёте не ослабляет identity gate. Текущая exact-name+unit policy принимает только строгую descriptive identity с source-owned specificity и полной проверкой ambiguity; generic name/number, fuzzy-only evidence или collision остаются REVIEW. История без stable 1C code сохраняет отдельную provenance каждой группы.

Historical prices всегда относятся к дате источника; availability остаётся `unknown`. Компания default `RUB` применяется только при отсутствующей валюте источника. Исторические цены не включаются в live/provider ranking или totals. Каждая history-backed sourcing run сохраняет версию каталога, с которой она выполнялась.

## Shared history access and coordination

`settings` остаётся ADMIN-only. Capability `one_c_history_import` выдана ADMIN и USER. USER видит в Settings только 1C history panel; системные settings/secrets/provider APIs остаются ADMIN-only. USER может выбрать сохранённый profile и корректировать mapping текущего импорта, но не может persist/update/delete глобальный profile.

Preview bound к authenticated owner и проверяется при inspect, analyze и final import. Лимиты — 3 pending previews на пользователя и 20 всего; действует TTL cleanup и нет cross-user eviction. Если final import получает busy 409, preview и mapping остаются доступными для retry.

`OneCHistoryActivityRegistry` использует shared leases для sourcing с 1C и exclusive lease для замены активного snapshot. Replacement отклоняется, пока есть history readers; после admission writer новые `one_c_only`/`one_c_then_provider` запросы отклоняются без silent fallback. `provider_only` не получает history lease и работает во время замены. Project держит lease до постановки job в очередь и затем до terminal worker completion/failure; submission failure также освобождает lease. Single-row lookup держит lease на всю операцию. Все history-backed rows одного project используют один captured catalog version; смешанные версии fail closed. Обновление snapshot атомарно активирует staging database, а старые отображаемые results остаются неизменными и получают только neutral stale-history notice.

Координация сейчас process-local. Поддерживаемый production topology для этой версии: Caddy → один Averon Import application process → один uvicorn process с одним worker. Multi-worker/multi-replica deployment требует cross-process/distributed lease; такой механизм сейчас не реализован и Redis не используется.
